# 開發協作流程 — 10 角色分工（多 agent 協同）

> 目標：讓**每一次開發**（新功能、新架構、修補、重構）都由多個角色 agent **協同、互相監督、互相協助**完成，
> 而**不是單一角色從頭做到尾**，藉此提升整體專案穩定度。
> 本文件是 [CLAUDE.md](../CLAUDE.md) 協調政策的詳細設計與操作手冊。
> 建立日期：2026-06-06。來源藍本：[參考-軟體開發10角色藍本](參考-軟體開發10角色藍本.md)。

---

## 0. 為什麼這樣做

- **Context 隔離**：每個角色獨立 context，後端 agent 不會被前端細節塞爆，反之亦然。
- **獨立把關**：寫程式的人不替自己的程式碼背書——測試／審查／資安由**不同角色**驗證，才抓得到盲點。
- **契約交接**：先有介面契約，各角色照契約並行開發，減少來回與整合衝突。
- **可靠的邊界**：用「角色職責＋工具權限」雙重約束，比單靠提示詞穩。

> 本專案採**一律完整管線**（使用者決策）：任何變更都走下述角色管線；以**平行分派**與**契約先行**控制延遲與成本，而非省略角色。

## 1. 角色定義（對應本專案）

> subagent 取自 `~/.claude/agents/`（已掛載 23 個）。以 agent 的 `name` 呼叫。

| # | 角色 | subagent | 在本專案的具體職責 | 寫碼權限 |
|---|------|----------|--------------------|----------|
| 1 | 架構師／協調者 | `Software Architect`（＝主執行緒） | 拆解需求、定義型別／API 契約、技術選型、整合驗收、仲裁 | 僅契約／文件 |
| 2 | 後端 | `Backend Architect` / `Senior Developer` | `server/` 業務邏輯、Fastify 路由（依契約）、串接 repository | `server/src/**` |
| 3 | 前端 | `Frontend Developer` | `src/` UI 元件／頁面／狀態、依 API 契約串接、a11y、響應式 | `src/**` |
| 4 | 資料層 | `Backend Architect`（含資料） | Prisma schema／migration、`repositories/` 存取介面、索引／完整性 | `server/prisma/**`、`server/src/repositories/**` |
| 5 | 測試／QA | `Test Results Analyzer` ＋ `Accessibility Auditor`、`Performance Benchmarker` | 設計／撰寫／執行測試、覆蓋率、依契約驗收、a11y（vitest-axe）、效能 | 僅 `*.test.*` |
| 6 | 程式碼審查 | `Code Reviewer` | 審 diff：bug、邊界、命名、重複、是否偏離契約 | 唯讀＋評論 |
| 7 | DevOps | `DevOps Automator` | `.github/workflows/`、`Dockerfile`、`docker-compose.yml`、env、pre-push hook | 基礎設施檔 |
| 8 | 資安 | `/security-review` skill ＋ `Code Reviewer`（資安視角） | 依賴漏洞、authz/authn、輸入驗證、注入/XSS/外洩、機密管理 | 唯讀＋報告 |
| 9 | 除錯 | `Minimal Change Engineer`（最小修補）/ `general-purpose`（調查） | 從 log/stack trace 反查根因、重現、最小修補 | 讀為主 |
| 10 | 文件 | `Technical Writer` | README、`docs/`、ADR、API 文件與實際行為同步 | 僅文件 |

### 對照藍本的三個缺口與處理
- **資料層**：本專案無獨立資料 agent，併入 `Backend Architect`（它本就涵蓋 DB／schema）；資料職責與後端邏輯職責**在同一 agent 內仍分階段**（先定 schema/repository 介面，再寫邏輯）。
- **資安**：用 `/security-review` skill（對當前 branch 變更做資安審查）＋ `Code Reviewer` 以資安視角複審。
- **除錯**：用 `Minimal Change Engineer`（只動與問題相關的最小範圍，不順手重構）或 `general-purpose` 做調查。

## 2. 管線：一個工作單元怎麼跑

```
            ┌─────────────────────────────────────────────┐
 Phase 0    │ 協調者：拆解 → 介面契約（型別/API/資料形狀）│  ← 契約未定不得開工
            │           → 技術選型＋理由（ADR 草稿）       │
            └───────────────┬─────────────────────────────┘
 Phase 1                    │ 資料層：schema/migration/repository 介面（涉及資料時）
            ┌───────────────┴─────────────────────────────┐
 Phase 2    │  後端（依契約）        ‖        前端（依契約）│  ← 平行
            └───────────────┬─────────────────────────────┘
 Phase 3    │  測試/QA  ‖  程式碼審查  ‖  資安稽核          │  ← 平行、獨立角色、唯讀＋產出
            └───────────────┬─────────────────────────────┘
 Phase 4                    │ 有問題 → 除錯定位根因 → 交回原開發角色修 → 重跑 Phase 3
 Phase 5                    │ DevOps：CI/CD、容器、env（涉及時）
 Phase 6                    │ 文件：與實際行為同步
 Phase 7                    │ 協調者整合驗收 → integration 分支提交（pre-push verify 機器把關）
```

### 平行 vs 順序
- **可平行**：後端 ‖ 前端（共用 Phase 0 契約）；測試 ‖ 審查 ‖ 資安（都對同一份 diff）。
- **必須順序**：契約（0）→ 資料層（1）→ 實作（2）→ 品質關卡（3）→ 整合（7）。
- **平行做法**：在同一則回應中對多個 subagent 發 `Agent` 呼叫；後續追問用 `SendMessage` 續用既有 agent（保留其 context、不重開冷啟動）。

## 3. 交接契約（handoff，靠檔案不靠口述）

| 交接 | 上游產出 | 下游依據 |
|------|----------|----------|
| 協調者 → 後端／前端 | `src/types/*.ts` 型別、API 端點與請求/回應 schema（zod）、行為約定 | 各自照契約實作，不自改契約 |
| 協調者 → 資料層 | 資料模型決策、實體關聯、需保存的欄位 | Prisma schema＋repository 介面 |
| 資料層 → 後端 | `VersionsRepository` 等存取介面（唯讀給後端） | 後端呼叫介面，不改 schema |
| 後端 → 前端 | 實際 API 行為（端點、狀態碼、錯誤格式） | 前端串接、處理 loading/error |
| 開發 → 測試/審查/資安 | 變更 diff、契約、驗收標準 | 各自驗證並**回報**（不改實作） |
| 品質關卡 → 除錯/開發 | 失敗清單、審查意見（必改/建議/可選）、風險（依嚴重度） | 除錯定位、原開發角色修正 |
| 各角色 → 文件 | API 實際行為、架構決策 | README/ADR/docs 同步 |

> **改契約的唯一路徑**：任何角色想改介面契約，先回報協調者；協調者更新契約並重新分派，**不允許下游私自變更**。

---

## 4. 驗收關卡（兩層把關，皆綠才算完成）

1. **角色把關（人/agent）**：測試/QA 通過驗收、Code Reviewer 無「必改」未解、資安無高嚴重度未解、文件已同步。
2. **機器把關（pre-push）**：`git push` 觸發 `.githooks/pre-push` → `npm run verify`（tsc + eslint + vitest 覆蓋率 + build）＋ 後端 `verify:server`（tsc + 測試）。紅的擋下。

> 兩層**互補不互相取代**：機器把關抓回歸與型別，角色把關抓設計、邊界、資安與可讀性。

---

## 5. 鐵則（違反即越權）

- **禁止單一角色包辦**：實作與驗證必為不同角色；協調者不親自寫業務碼／測試。
- 後端不改前端、不自改 API 契約；前端不改後端、不直接碰 DB。
- 資料層只提供存取介面，不寫業務邏輯。
- 測試/審查/資安**只回報不改實作**（避免「改實作讓測試過」）。
- 除錯只動與問題相關的最小範圍，不順手重構。
- DevOps 不改業務碼；未確認不對正式環境做不可逆操作。
- 文件不改程式邏輯。

## 6. 實例：新增「員工到職日」欄位（跨層小功能也走完整管線）

1. **協調者**：在 `src/types/org.ts` 的 `Employee` 加 `hireDate?: string` 契約；決定後端是否需保存、是否影響 schemaVersion；產出工作拆解。
2. **資料層**：若要雲端保存 → 評估 JSONB 文件已含此欄位（無需 migration）；若 P4 後正規化 → 加欄位＋migration。
3. **實作（平行）**：後端確認 `/api/versions` 寫入含新欄位；前端 `EmployeeForm` 加輸入、`OrgDetailPanel` 顯示。
4. **品質關卡（平行）**：測試/QA 補 `EmployeeForm` 與 `orgOperations` 測試 ＋ a11y；Code Reviewer 審 diff；資安檢查輸入驗證（日期格式）。
5. **除錯**：若 migration 測試紅 → 除錯定位 → 交回資料層修。
6. **文件**：Technical Writer 更新 README 資料格式表與系統設計文件 §5。
7. **協調者**：整合 → `integration` 提交（pre-push 兩層皆綠）→ 標準 PR 自動更新。

> 即使是「加一個欄位」，仍經過契約→實作→獨立驗證→文件，**沒有任何一個角色獨自完成全部**。

---

## 7. 反面模式（要避免）

- ❌ 協調者自己把功能寫完再「補一個 review」走形式。
- ❌ 後端順手改前端（或反之）以「比較快」。
- ❌ 測試 agent 為了讓測試通過去改業務碼。
- ❌ 下游角色私自更動 API 契約而不回報協調者。
- ❌ 為了省事略過資安/文件角色。
- ✅ 正解：契約先行、平行分派、獨立把關、問題回報原角色修、兩層驗收皆綠。
