# 介面契約 — 階層由「主匯報深度」自動計算（level 退為覆寫）

> 協調者產出。使用者回報工作台佈局「沒有改善、階層線數字也錯」，並問「階層線是否從組織資料帶過來」。
> 根因確認後定案。使用者決策：**自動算為主＋保留手動覆寫**（AskUserQuestion 2026-06-07）。
> 狀態：開工。最後更新：2026-06-07。

## 1. 根因（已用執行中 App + 資料雙重確認）

- 階層線（垂直層帶）與多處邏輯都直接讀 `assignment.level` 這個**手維護整數**。
- 實際資料（localStorage draft）`level` 存的是「職等」概念：**王大明（根）與其 4 名直屬全是 level 1** → 主管與部屬被放同一條層帶，匯報線「看不出階層」。另一份（8088 發布版）層數從第 2 層起跳。
- 病根：**手維護的 `level` 與真實匯報深度不一致**，且：
  - `buildOrgFlowGraph` 的 dummy 跨層、父置中都「信任」這個錯 level → 救不了。
  - `resolveLevels` 缺 level 時的 dagre-rank 後備被**虛線/跨維度矩陣邊**污染（直屬被打散到不同層）。
- **連帶**：`assignment.level` 還被 `orgHealth`（層級深度健檢）、`bpmnSimulator`（requesterLevel）讀取 → 資料錯時這些指標也錯。

## 2. 定案設計：單一真實來源 = 主匯報深度，`level` 退為覆寫

### 2.1 新服務 `src/services/reportingDepth.ts`
```
computePrimaryDepth(assignments: Assignment[]): Map<string /*employeeId*/, number>
```
- 範圍 = 傳入的 assignment 集合（即「目前視角」：全公司＝全部 active 組別歸屬；單組＝該組歸屬）。
- 每位員工的「正規父」= 其**顯示歸屬**（`isPrimaryGroup` 優先，否則第一筆，與 `buildOrgFlowGraph.pickDisplayAssignment` 一致）的 `primarySupervisorId`。
- 父為 null 或父不在集合內 → 該員工為根，depth = 1；否則 depth = 父 depth + 1。**只走主匯報（primarySupervisorId），忽略 supervisorIds 的虛線**（避免污染）。
- 有環防護（理論上已被 validators 擋）。
```
effectiveLevel(assignment: Assignment, depthMap: Map<string,number>): number
  = assignment.level /*覆寫*/ ?? depthMap.get(assignment.employeeId) ?? 1
```
- **覆寫優先、否則用計算深度**（= 使用者選的 B）。

### 2.2 `buildOrgFlowGraph`（佈局）
- `resolveLevels` 改為：`levelMap[node] = effectiveLevel(displayAssignment, depthMap)`，depthMap 由 `computePrimaryDepth(groupAssignments)` 算。
- **移除 dagre-rank 後備整段**（不再需要；計算深度即是乾淨層級）。
- dummy 跨層通道、父置中、層帶 Y、同層去重疊：**沿用現有**，但現在吃乾淨的層級 → 同主管直屬同層、主管恰在部屬上一層、跨層虛線邊有 dummy 通道不穿節點。
- 層帶標籤 `第 N 層`：N = 計算深度（根 = 第 1 層）。

### 2.3 `orgHealth`（層級深度健檢）
- 第 383–397 行的 `const level = primary.level ?? 1` 改用 `effectiveLevel(primary, depthMap)`，depthMap 由 `computePrimaryDepth(normalized.assignments)` 算一次。
- 結果：maxDepth／perLevel 反映真實匯報深度（根 = 第 1 層），不再被怪 level 污染。

### 2.4 `bpmnSimulator`（requesterLevel / requesterOrgLevel）
- 兩處 `primaryAssignment(.)?.level ?? (null|...)` 改用 `effectiveLevel`（需傳入 / 算 depthMap，範圍取該 requester 主歸屬所屬視角的 assignments；最小改動即可，重點是不再讀生 level）。
- `SimulationExpenseForm` 顯示「組內層級：第 N 層」隨之正確（讀 ctx 傳下來的值，不需自行算）。

### 2.5 拖曳語意（`OrgFlowChart.onNodeDragStop`）
- **drag-to-reassign（拖到主管節點上）**：維持；**新增**：reassign 成功時**清掉被拖者該歸屬的 `level` 覆寫**（`level: undefined`），讓他跟隨新主管的計算深度（「換了主管、層級自然跟著走」）。改在 `reassignSupervisor`（orgOperations）內處理。
- **垂直拖曳（未命中節點）**：簡化為「設定該節點 `level` 覆寫 = `levelFromTopY(y)`」單點，**移除「把其他所有人往下移一層」的 cascade**（第 223–229 行；那段正是散播怪 level 的來源）。即只 `upsertAssignment({...assignment, level: newLevel})`。

### 2.6 Migration v2 → v3（清掉非預期的舊 level）
- `ORG_SCHEMA_VERSION` 2 → 3；新增 `toV3`：把**所有** `assignment.level` 設為 `undefined`（移除欄位值）。
  - 理由：現存 level 是佈局產物/職等殘值，**非使用者刻意覆寫** → 清掉後一律走計算深度＝乾淨。之後使用者垂直拖曳才會產生真正的稀疏覆寫。
  - `toV1` 既有 `backfillAssignmentLevels` 不動（歷史 migration 不改）；其回填值會被 `toV3` 清除，淨結果 level = undefined。
- `Assignment.level` 型別註解更新為：「可選的**層級覆寫**；預設由主匯報深度自動計算，僅使用者刻意垂直拖曳時設值。」
