## 1. 專案概述

**定位**：一個以**人事（HR）為出發點**的組織**規劃／試算**工具（前端優先）。它讓 HR 沿**兩個維度**思考如何規劃組織——**reporting line（匯報線／階層部門）× 專案職能（跨部門）**——並以 [React Flow](https://reactflow.dev/) 視覺化兩維度的組織關係。所有調整都先在草稿／快照中試算，可比對 diff、發布版本，降低異動風險。前端可獨立運作（localStorage），並提供 **opt-in 後端**做雲端版本持久化。

**BPMN 的角色**：BPMN **不是要開發的營運系統**，而是一個**輔助的組織變更影響分析透鏡**——幫人事理解組織調整後對整體作業／決策流程的影響（哪條簽核路徑斷鏈、哪個關卡成為單點風險）。本工具**不是一套全公司日常都在用的營運系統**。

**目標使用者**：HR / 組織治理人員（組織規劃者）。

**核心價值**：
- **雙維度組織規劃**：以「匯報線 × 專案職能」兩維度建模——`Group.kind` 區分**階層部門**（走 parentId 的匯報線）與**跨部門專案職能**；支援「一人多組、每組可有不同主管」的矩陣組織，並以雙視角呈現。
- **安全試算**：所有變更先在草稿與快照中進行，可比對 diff、可發布版本，降低調整風險。
- **職能視角**：以職能維度檢視覆蓋缺口（無成員職能）、無 lead 職能與跨職能負載，輔助規劃判斷。
- **變更影響透鏡（輔助）**：以 BPMN 流程為透鏡，於組織變動時健檢出簽核路徑的**斷鏈**或**單點風險（SPOF）**，理解異動對作業流程的衝擊。

**關鍵特性**：資料預設自動存於瀏覽器 `localStorage`，可匯出／匯入 JSON 做版本保存與共享；另可選擇啟用後端（`VITE_API_URL`），將發布版本與草稿持久化到 PostgreSQL，前端不啟用時完全不依賴後端。

## 2. 系統範圍

### 〔現有〕涵蓋功能
- **總覽頁 + 規劃旅程地圖**：首頁 `/` 呈現「載入 → 編輯 → 健檢 → 比較 → 影響 → 發布」六步固定順序的規劃旅程，每步顯示完成狀態（done/ready）並可直接點擊跳至對應頁面；上方智慧 CTA 卡片由純函式 `overviewStatus.ts` 依資料／版本／流程狀態推導**建議的下一步**（無資料→匯入、有資料未發布→規劃健檢、僅 1 版本→情境比較、>=2 版本且有流程未設基準→變更影響，其餘→規劃健檢）；下方狀態小卡呈現活躍員工／部門／職能／已發布版本／已定義流程
- **改善 Roadmap 頁面**：`/roadmap` 顯示**未來改善方向 + 完成進度**——綜合 PM／UXR／變革管理顧問三方評審後的改善計畫，分 Phase 0–5 + 觀察項；每個 item 顯示狀態（done/in-progress/planned/researching/observing）、規模（S/M/L）、來源徽章（PM／UXR／CM／共識），已完成項目附 commit hash 與完成日期；頁面另列**紅線清單**（三方共識「不該做」）與**8 個訪談驗證問題**（標記為「待訪談」的項目強烈建議先訪談 3–5 位真實 HR 再動）。資料源為 hard-coded 純資料 + 純函式（`roadmap.ts`），事實來源同步 [規劃-改善Roadmap](規劃-改善Roadmap.md)
- 員工 / 組別 / 職級 / 組別歸屬（assignment）的維護
- **專案職能雙維度**（`Group.kind`：部門／職能）：部門走匯報線（parentId），職能為跨部門扁平；表單可選種類、列表以徽章標示
- **職能視角**：覆蓋缺口（無成員職能）、無 lead 職能、跨職能負載（一人隸屬多職能）的彙總呈現
- **規劃健檢**：由當前組織資料即時推導量化指標與警示——管理幅度（span of control）、層級深度、職能覆蓋缺口、結構風險（斷鏈／匯報循環／單點風險 SPOF）、**組別↔主管一致性**（`group-mismatch` 主管不在新組／層級異常、`parallel-colead` 合法平行共管標示）；另含**規劃就緒度（結構面 0–100）**——由 findings 推導 4 個結構維度分數與整體等級，誠實命名「結構面」（不含 leadership／comms／sponsor 等變革要素）
- **規劃情境比較 what-if**：並排最多 4 個版本（含內建種子、mock、發布版本、雲端版本）；以基準（陣列首個有效情境）為 base 算結構差異（重用 `computeOrgDiff`），同時對齊規劃指標矩陣（重用 `buildOrgHealth`），協助 HR 試算多案後選擇；另含**保留事項（未變動歸屬比率）**——從 diff 反推「相對基準有多少配置維持不變」，給員工安定感 anchor
- 組織圖雙視角（匯報組織圖、組別歸屬圖）與圖上直接編輯；組別歸屬視角可依「全部／部門／職能」過濾
- 編輯模式快照（snapshot）與差異著色（diff）
- 變更歷程（changelog）與前後狀態 diff 檢視
- CSV / Excel（.xlsx）匯入（員工 × 組別）→ 產生組織 JSON
- 資料版本管理：草稿、內建種子／mock、發布版本、匯出入
- **版本生效日**：發布版本可指定生效日（排程生效），下拉顯示「排程／已生效」

## 3. 整體架構

前端為 SPA，分為四層；後端為**選用**的版本／草稿持久層（未啟用時整條虛線都不存在）。

```
┌─────────────────────────────────────────────────────────┐
│  視覺化 / UI 層                                            │
│  React Flow 畫布、shadcn/ui 元件、頁面與表單              │
├─────────────────────────────────────────────────────────┤
│  狀態管理層（React Context）                               │
│  OrgProvider（組織資料）  /  BpmnProvider（流程與模擬）   │
├─────────────────────────────────────────────────────────┤
│  服務層（services/，純函式商業邏輯）                       │
│  圖形建構、diff、模擬器、影響分析、版本、生效日、         │
│  CSV/xlsx、匯出入、apiClient（後端存取）                  │
├─────────────────────────────────────────────────────────┤
│  資料層                                                    │
│  localStorage（草稿/版本/流程） + 檔案 I/O（JSON/CSV/xlsx）│
│  內建種子 src/data/org-data.json、mock、bpmn-defaults     │
└───────────────────────────┬─────────────────────────────┘
                            ┊  VITE_API_URL 啟用時（opt-in）
┌───────────────────────────┸─────────────────────────────┐
│  後端 API（server/，Fastify + Prisma）                    │
│  REST：/api/versions、/api/draft、/api/health             │
│  repository 抽象（記憶體 / Prisma 實作）                  │
├─────────────────────────────────────────────────────────┤
│  PostgreSQL — OrgVersion / OrgDraft（JSONB 文件快照）     │
└─────────────────────────────────────────────────────────┘
```

**資料流向（前端）**：
1. 使用者編輯 → React state 更新 → 自動寫入 localStorage 草稿
2. 重新整理 → 優先載入 localStorage 草稿；無草稿則載入當前「已發布版本」
3. 匯出 → 下載帶時間戳的 JSON；匯入 → 取代當前資料，可選擇發布為新版本
4. 流程模擬時，於送出當下擷取請款人的組織快照（orgContext），確保模擬結果可重現

**資料流向（啟用後端時）**：
5. 啟動時 `apiClient.listVersions()` 載入雲端版本，與本機版本依 id 去重後併入版本下拉
5b. 雲端載入回來後挑「進場預設版本」：**有未發布草稿則保留草稿；否則自動切到最新的雲端版本**（最新＝`publishedAt` 最新，由 `pickLatestRemoteVersionId` 挑）；自動切換最多一次，且不覆蓋使用者手動選版／剛匯入／正在編輯的內容。後端未啟用／雲端無版本／載入失敗時維持本機預設。詳見 §7 OrgProvider 與 [契約-預設最新雲端版](契約-預設最新雲端版.md)
6. 發布／刪除版本 → 先更新本機，再**寫穿**到後端（best-effort，失敗僅 `console.warn`，不阻斷本機操作）
6b. **離線偵測 + 未同步提醒（階段 B1）**：`useOnlineStatus` 被動偵測瀏覽器線上／離線；發布寫穿雲端失敗或發布當下離線 → `OrgProvider` 標記 `pendingCloudSync`（持久化於 localStorage、下次成功發布清除），全站置頂 `CloudSyncBanner` 據此顯示「離線中」或「有本機變更尚未同步」。**本切片只偵測＋提醒、不自動補同步**（離線發布佇列／回線自動補推屬後續階段 B2）。詳見 §7 OrgProvider 與 [契約-離線偵測與未同步提醒](契約-離線偵測與未同步提醒.md)
7. 後端以 JSONB 文件保存整包 `OrgData` 快照（P4 才正規化為實體表）

**組織圖三視角**（自 2026-06-08 由雙視角擴為三視角，新增「組別組織圖」）：

> 三者各自回答不同問題、互不取代、皆可回滾——**匯報組織圖**＝「誰向誰匯報」（每人一節點、依匯報線排層）；**組別歸屬圖**＝「每筆組別歸屬」（同一人跨組會多節點、唯讀檢視矩陣 membership）；**組別組織圖**＝「以組別為主」（每人一節點、**員工攤平在一張連貫圖上**、同組靠隱藏 X 欄位網格吸附對齊聚在一起並以**背景分區**標示、匯報線含跨組邊，Phase D 先唯讀）。`WorkbenchPage`／`/workbench` 以視圖切換 Tabs「匯報組織圖／組別組織圖」在前兩種主視圖間切換（預設匯報，與既有並存可回滾）；組別歸屬圖維持在 `/org-chart` 的視角切換。

- **匯報組織圖**：節點＝人員，連線＝匯報關係（實線＝主匯報、虛線＝其他主管）。
  - **匯報線標籤（自訂 `ReportingEdge`，自 2026-06-07）**：邊改用自訂 edge `type:'reporting'`（`src/components/orgFlow/ReportingEdge.tsx`），標籤「主匯報／虛線匯報」以 `EdgeLabelRenderer` 渲染為**白底、置中坐在線水平段上、與線平行**的文字（`backgroundColor:'var(--background)'`／`padding:'0 4px'`／`borderRadius:2`），白底只遮文字底下那一小段線、**線從白底背後直直連續穿過、不再被白底標籤切成兩段**。線型（實線／虛線）、箭頭、路由（smoothstep + dagre）與原一致——**佈局／路由演算法不變**，僅標籤渲染改造。`label`／`isPrimary`／`offset` 放在 `edge.data`（標籤文字讀 `data.label`、空則不渲染；`data.isPrimary` 決定線型且 `centerParents` 仍依賴它），不再用頂層 `label`/`labelStyle`。`OrgFlowChart` 以穩定參考註冊 `edgeTypes={{ reporting: ReportingEdge }}`；標籤 `pointerEvents:'none'` 不擋互動。（標籤定位曾短暫採「透明底、浮在線上方」，因線看似繞過字而**反轉為現況白底坐線上、線穿過**。）契約見 [契約-邊標籤改造](契約-邊標籤改造.md)。
  - **層級＝主匯報深度，自動計算（自 2026-06-07）**：層帶（垂直層）由**主匯報深度**決定——根（無主管者）＝第 1 層、每往下一階 +1、主管必在部屬上一層；沿 `primarySupervisorId`（主匯報）計算、**忽略虛線/次要主管**（不被矩陣關係污染）。這是組織圖層帶、健檢層級深度與 BPMN 申請人層級共用的**單一真實來源**（純函式 `reportingDepth.computePrimaryDepth`）。`assignment.level` 不再直接決定層帶，而是退為**稀疏的「手動覆寫」**：預設不設值（走自動計算），使用者**刻意垂直拖曳**某節點時才寫入覆寫值（覆寫優先於計算深度、單點不向下連動子樹）；**拖人到新主管節點（drag-to-reassign）會清掉其層級覆寫**，讓他自動落到新主管下一層。契約見 [契約-階層由匯報深度計算](契約-階層由匯報深度計算.md)。
  - **佈局直觀化（自 2026-06-07）**：同一主管的直接部屬聚集在父節點下方（父水平置中於直接部屬），跨層匯報線的水平段落在層與層之間、不被中間層節點遮蔽——例如某 L3 主管的 L4／L5 部屬一眼可辨。做法見 `buildOrgFlowGraph.ts` 佈局管線（跨層邊插 dummy 中繼節點保留水平通道、父置中、層間路由）。契約見 [契約-工作台佈局與預設視角](契約-工作台佈局與預設視角.md)。
  - **drag-to-reassign（拖拉改匯報線，階段 3）**：在編輯模式把某人節點**拖到另一名員工節點上＝把他的主管改成那個人**。`OrgFlowChart.onNodeDragStop` 以 React Flow v12 `getIntersectingNodes` 偵測 drop target（過濾掉自己與 `ghost-*` 節點，取最上層員工節點）：**命中**＝呼叫純函式 `reassignSupervisor` 改主匯報線（**並清掉被拖者該歸屬的 `level` 層級覆寫**，讓他跟隨新主管的計算深度落到下一層；成功 `onDraftChange` 重繪、由 dagre 重新佈局；失敗＝**循環／inactive／自我指派**等則**不套用**、把被拖節點視覺位置回滾並以短暫 `Alert` 顯示原因）；**未命中（垂直拖曳）**＝走 level 層級邏輯：對被拖節點寫入單點的 `level` 層級覆寫（覆寫優先於計算深度、不向下連動子樹）。拖曳過程（`onNodeDrag`）以 `isDropTarget` **hover 高亮**可放置目標，讓使用者知道「放開會掛到這個人下」；drop 採 hover 當下已算的 target（所見即所得）。**循環防護**：套用後以 `detectReportingCycleFromAssignments` 檢查整體匯報關係，偵測到循環整筆不套用並回滾。**鍵盤替代**：拖拉本身無鍵盤替代，但**既有的連線（`onConnect`）與詳情面板（`OrgDetailPanel` 編 `supervisorIds`）為鍵盤可達的等效路徑**，明訂保留不退化。**`/workbench` 與 `/org-chart` 兩頁共用同一 `OrgFlowChart` 畫布，drag-to-reassign 同時生效**；後端零改動。
- **組別歸屬圖**：節點＝每筆組別歸屬，同一人跨組會出現多個節點；含組別標籤節點與外部主管節點。可依「全部／部門／職能」過濾（接 `buildGroupMembershipGraph` 的 `kindFilter`）；當目前過濾與「選定的單一組別」種類不符時，會自動切回「全部視角」，避免空白畫面。**唯讀 membership 檢視**，與下方「組別組織圖」用途不同（後者每人一節點、以組別為主、為後續可編輯的主視圖）。
- **組別組織圖（以組別為主，`buildGroupOrgGraph` + `GroupOrgFlowChart`，Phase D 唯讀，自 2026-06-08；2026-06-08 重設計為「一張連貫圖 + 同組背景分區 + 隱藏 X 欄位網格對齊」）**：把工作台主視圖改為**以組別為思考主體**，但呈現方式是**一張連貫的組織圖**——員工為**頂層攤平節點**（`type:'employee'`、**無 `parentId`**，不再是群組框的子節點），匯報線照常呈現（含**跨組匯報邊**）；**同組的人靠「隱藏 X 欄位網格」吸附對齊聚在一起**、再用**背景分區（`groupZone` 節點）**標示「這一片是哪一組」，而非把成員框進一個容器。（**取代先前設計**——先前是「每組一個 React Flow 群組框 parent node + 成員為子節點 + 框內第 N 層層級線 + 群組框 Handle 錨定組間 `group:parent→group:child` link 邊」，已全數移除。）
  - **每人一節點**（取其在該組的 assignment），與「組別歸屬圖每筆歸屬一節點」不同；組別組織圖的單位是「人在這組」。節點 id 作用域化為 `${groupId}::${employeeId}`，以容許同一人在多組各有節點。
  - **背景分區（`groupZone` 節點，取代群組框）**：每組一個背景**色塊**節點（淡色、**每組不同 hue**），角落帶標籤（組名／組長／共管徽章），用來**標示同組成員聚集的區域、不是把成員框起來**。屬**背景層**（`zIndex: 0`、`pointer-events-none`、不可選／不可拖／不可連線）。**分區尺寸依「吸附後成員的實際 bounding box」回推**——以該組成員攤平、吸附完成後的座標算外接矩形再加 padding，故分區**永遠包住其成員**、不會與成員錯位。**無框、無框內層級線、無容器邊界約束（成員不再 `extent:'parent'`）**。
  - **隱藏 X 欄位網格（grid＝對齊輔助，非可見線）**：grid 是**像 Bootstrap 那樣的隱藏對齊輔助**——只用來吸附節點 X、**不畫任何可見格線、也不把組框起來**。攤平後每個成員的 X 以 `snapXToGrid(x) = Math.round(x / COLUMN_WIDTH) * COLUMN_WIDTH` 吸附到格點，`COLUMN_WIDTH = ORG_FLOW_NODE_WIDTH(200) + ORG_FLOW_NODE_SEP(60) = 260`；同層去重疊時仍維持格點，使**跨組／跨層的欄位互相對齊、整體工整**。Y 維持層帶（依層級分層）。
  - **匯報邊（含跨組）**：成員 `supervisorIds` 連出匯報邊（`type:'reporting'`，主匯報實線／其他主管虛線）；因員工已攤平在同一張圖、**主管與部屬不在同一組時的「跨組匯報邊」（`go-cross-*`）也照常連起、不再被群組框隔開**。組與組的部門上下層關係**由跨組匯報線 + 背景分區的上下位置共同呈現**——不再用獨立的 `group:parent→group:child` 組間 link 邊與群組框 Handle。
  - **co-leader 與組長同層**：佈局時把推導出的平行共管（co-lead）`level` 鉗到組長同層（重用 `effectiveLevel` 覆寫語意），呈現「業務部由 CEO（組長）＋ COO（平行共管）共管」這類同層共治；co-lead 由 `groupLeadership.deriveGroupLeadership` 即時推得（不落地）。
  - **唯讀（Phase D）**：本階段只看不改；**拖曳改組屬 Phase E**（新純函式 `reassignEmployeeGroup` + 雙手勢分流，待續）。佈局服務見 §6 `buildGroupOrgGraph.ts`；背景分區元件 `GroupZoneNode`（取代先前 `GroupBoxNode`）。計畫見 `.claude/plans/toasty-tumbling-turtle.md`。
- **職能視角面板**（`FunctionCoveragePanel`，於全部／職能過濾時顯示）：呈現 `buildFunctionCoverage` 的關鍵訊號——無成員職能、無 lead 職能、跨職能負載前幾名。

**規劃健檢頁（`/health`）**：以 `buildOrgHealth` 即時推導，分五區呈現——摘要卡片（在職人數、部門／職能數、主管數、平均管理幅度、警示數）、管理幅度（過寬／過窄主管清單）、層級深度（各層人數）、職能覆蓋（重用 `FunctionCoveragePanel`）、結構風險警示清單（findings，severity 以 Badge 標色）。
- **管理幅度**以**主匯報線**計：員工直屬主管＝其主歸屬 assignment 的 `primarySupervisorId`，只計 active 員工與 active 主管；標示過寬（> 門檻，預設 8）與過窄（= 1，潛在冗餘層級）。
- **層級深度**取每位員工主歸屬的**有效層級**（`reportingDepth.effectiveLevel`）——預設為**主匯報深度**（`computePrimaryDepth`：根＝第 1 層、每階 +1、只走主匯報忽略虛線），`assignment.level` 為手動覆寫時優先。此為**目前視角內的匯報深度**（根＝第 1 層、主管恰在部屬上一層），不再被手填或殘留的怪 `level` 污染。
- **組別↔主管一致性（findings，自 2026-06-08，Phase F）**：以 `groupLeadership.deriveAllGroupLeadership` 推得的組長＋平行共管為基礎，產出兩類 finding——**`group-mismatch`（warning，掛就緒度 `structure` 維）**：①「主管不在新組」＝成員的組外主管**不夠格**當共管（非 `groupLeadership.isLeadLevel`：既非無上級主管、亦非任何組組長）時警示，疑似把成員掛錯組；②「層級異常」＝組內主管但其部屬的有效層級未低於主管（部屬應在主管下一層）。**`parallel-colead`（info，不計就緒度）**：組外主管**夠格**當共管時，標示為與組長同層的合法平行共管（例：CEO＝組長、COO 帶部分成員→COO 為平行共管），只標示、不視為問題。三規則皆過濾 active（離職員工/主管、停用組不誤報）。

**規劃情境比較頁（`/compare`）**：上方一排「情境槽」（最多 4 個），每槽是版本下拉（沿用 `useOrg().dataVersions`，含內建種子、mock、發布版本、雲端版本）；無效版本選項 disabled 並標「✗（格式錯誤）」、其他槽已選的 id 也 disabled 避免重複。首槽預設為當前 active 版本；第一個「有選版本且 valid」的槽自動成為基準（`baselineSlotIndex`），若不在第 0 槽會出現 callout「目前基準＝第 N 槽（…版本名）」。所有槽當 `slots.length > 1` 時都可刪。至少 2 個有效情境才會呈現對照區塊，由上而下：情境槽列（含健檢摘要小卡——在職人數、部門／職能、警示數）、規劃指標對照表（渲染 `metricMatrix`）、結構差異摘要卡（每個非基準情境一張，呈現 `diffSummary`）。
- **指標對照著色**：對 `direction='down'` 的指標（警示數、無成員職能數、無 lead 職能數、單點風險 SPOF 數），最大值用 warning、最小值用 success 標色；全相同則不上色，避免暗示。其餘指標（在職人數、部門數、職能數、主管數、平均管理幅度、最大層級深度）為 `neutral`，不上色。
- **後端不涉及**：頁面為純前端推導，沿用 `useOrg().dataVersions` 取得各版本 OrgData。

## 5. 資料模型

型別定義位於 `src/types/`。

### 組織核心（`src/types/org.ts`）
- **`Employee`** — 員工：`id`、`employeeNo`（工號）、`name`、`status`（active/inactive）
- **`Group`** — 組別：`id`、`code`、`name`、`parentId`（階層父節點）、`status`、`kind`（`GroupKind`）、`leaderId?`（組長）
  - **`kind: GroupKind`**（`'department' | 'function'`，required）：`department`＝**階層部門**，沿 `parentId` 構成匯報線；`function`＝**跨部門專案職能**，v1 為扁平（`parentId` 應為 null）。舊資料由 migration 回填為 `'department'`。
  - **`leaderId?: string | null`**（組長，自 2026-06-08，「組別為主工作台」升級地基）：指向該組「組長」的 `employeeId`；選填、可為 null（＝未指定／空組）。**migration `toV4` 以「組內匯報根」回填**缺漏的 `leaderId`（已有值不覆蓋、空組為 null）。**可由 `GroupForm` 手動設定（Phase B）**——表單新增「組長」下拉，選項為該組成員、含「未指定」sentinel（選之＝null）；無成員時下拉停用。值走既有 `upsertGroup` 寫入 `Group.leaderId`。`leaderId` 是唯一**落地**的領導欄位；**co-leader（平行共管）為推導不落地**——由 `groupLeadership.ts` 即時算出，不進 schema/migration（與「層級不落地、即時計算」哲學一致）。詳見 §6 `groupLeadership.ts`。
  - 驗證（`validators.ts`）：`department` 的 `parentId` 須指向另一個 `department`；`function` 不可有 `parentId`；`isPrimaryGroup === true`（主歸屬／home line）的 group 應為 `department`，指向 `function` 會回報。
- **`JobLevel`** — 職級：`id`、`code`、`name`、`rank`（數字大小代表高低，供條件判斷）
- **`Assignment`** — 組別歸屬（核心關聯）：`employeeId`、`groupId`、`jobLevelId`、`supervisorIds[]`、`primarySupervisorId`、`isPrimaryGroup`、`level?`（**層級覆寫**：稀疏、選填；預設由主匯報深度自動計算（`reportingDepth.computePrimaryDepth`），僅使用者刻意垂直拖曳時設值）
- **`ChangeEntry`** — 變更紀錄：`timestamp`、`operator`、`changeType`、`summary`、`before?`/`after?`（JSON 字串）
- **`OrgData`** — 整包資料：`schemaVersion`（結構版本，migration 用）、`version`（內容版本，發布遞增）、`exportedAt`、`employees[]`、`groups[]`、`jobLevels[]`、`assignments[]`、`changeLog[]`

> **設計重點**：`Assignment` 是矩陣組織的關鍵——主管與職級掛在「歸屬」上而非「員工」上，因此一人可在不同組有不同主管／職級。

### BPMN 流程（`src/types/bpmn.ts`）
- **`BpmnProcess`** — 流程：`nodes[]`、`edges[]`、`approvalThresholds[]`（職級→可簽核上限金額）、`status`、`version`
- **簽核人解析模式 `ApproverResolutionMode`**：`byJobLevel`（依職級）、`directSupervisor`（直屬主管）、`groupJobLevel`（組內指定職級）、`orgHierarchy`（沿匯報鏈往上至 rank 達標）
- **`SimulationSession`** — 模擬會話：`formData`（請款表單）、`resolvedPath[]`、`resolvedApprovers`、`orgContext`（送出時的組織快照）、`logs[]`、`status`
- **`ImpactBaseline`** — 影響分析基準：`capturedAt`、`label`、`data`（組織快照）

### 編輯工作階段（`src/types/editSession.ts`）
- **`OrgDiffResult`** — 各種變更集合（新增／移除／修改的員工、歸屬、邊）
- **`EditSnapshot`** — 編輯快照：`orgData` + `nodePositions`（組織圖節點座標）

## 7. 狀態管理

### `OrgProvider`（`src/context/OrgProvider.tsx`、`orgContextState.ts`）
- 管理組織資料、版本清單、當前版本、操作者
- localStorage keys：
  - `hr-org-draft` — 草稿（自動儲存）
  - `hr-org-active-version` — 當前選定版本
  - `hr-org-published-versions` — 本機發布版本清單（於 `publishedVersions.ts`）
- 主要操作：`selectDataVersion`、`publishVersion`、`saveEmployee`、`saveGroup`、`saveAssignment`、`removeEmployee`、`removeAssignment`、`loadFromFile`、`exportData`、`applyChange`
  - **`publishVersion(draft, opts?)`**：簽章為 **options 物件** `opts?: { label?: string; note?: string; effectiveDate?: string }`（R4.3 由位置參數改為 options），回傳新版本 id；`onPublish` 同步採 options。`note`（調整理由）為本機 metadata，**不寫穿雲端**。
- **雲端版本接線（opt-in）**：`isApiEnabled()` 為真時——
  - 啟動以 `apiClient.listVersions()` 載入雲端版本，存於獨立的 `remoteVersions` state（與本機 `dataVersions` 分開，避免本機重整覆寫雲端清單）；下拉清單 = 本機 ＋ 雲端（依 id 去重）。
  - `publishVersion(draft, { label?, note?, effectiveDate? })` 先建立本機發布版本，再寫穿 `apiClient.publishVersion`（`note` 為本機 metadata、**不寫穿**）；`deletePublishedVersion` 依該 id 屬本機或雲端各自刪除。
  - 所有雲端呼叫為 **best-effort**：失敗只 `console.warn`，不阻斷本機編輯與發布。
- **未同步狀態追蹤 `pendingCloudSync`（離線優先同步階段 B1，僅 `isApiEnabled()` 時有意義）**：對外經 OrgContext 暴露「**有本機已發布變更尚未成功上雲**」旗標。
  - **標記時機**：`publishVersion` 內 best-effort 寫穿 `apiClient.publishVersion(...)` `.catch` 失敗時，或發布當下 `!navigator.onLine` → 設 `true`。
  - **清除時機**：`apiClient.publishVersion(...)` `.then` 成功時 → 設 `false`（代表已同步上雲）。
  - **持久化**：存 localStorage（key `hr-org-cloud-sync-pending`），重整後仍正確反映「有本機變更未上雲」；載入時讀回。後端停用時恆為 false。
  - **邊界**：本切片只「**記錄＋顯示**」，**不自動重送**；使用者要清除可透過下次成功發布。全站置頂 `CloudSyncBanner`（`src/components/`，掛於 `Layout`）依 `useOnlineStatus().isOnline` 與 `pendingCloudSync` 決定三態（離線中／有未同步／不顯示），dev 5174（無後端）一律 render null。**回線自動補同步屬後續階段 B2、本次未做**。契約見 [契約-離線偵測與未同步提醒](契約-離線偵測與未同步提醒.md)。
- **進場資料版本預設選取（草稿優先 → 最新雲端 → 本機 fallback，自 2026-06-07）**：進入 App 時「預設選哪個版本」依序判斷——
  1. **有未發布的本機草稿（相對所屬版本有變更）→ 保留草稿、不切走**（最高優先）。「有草稿」＝沿用的草稿屬於 active 版本，且相對版本資料有未發布變更（比較以 `fingerprintOrgData` 排除 `exportedAt`／`changeLog` 等易變欄位，避免誤判）。
  2. **否則，後端啟用且雲端有版本 → 預設選最新的雲端版本**（依發布時間 `publishedAt` 最新者；由純函式 `pickLatestRemoteVersionId`（`dataVersions.ts`）挑選，時間相同以 id tiebreak）。因雲端為非同步載入，採「初始用本機預設 → 雲端載入回來後若仍符合條件才自動切換一次」（`autoDefaultToLatestRemote`）。
  3. **否則（後端未啟用／雲端無版本／載入失敗離線）→ 維持本機預設**（`pickDefaultVersionId`，即 seed 或上次選的版本），與既有行為一致。
  - **不覆蓋使用者意圖**：自動切換最多執行一次（`autoDefaultLockedRef`），且不會覆蓋使用者**手動選的版本**（`selectDataVersion` 設 `userHasManuallySelectedRef`）、剛**匯入的檔案**（`loadFromFile`）或**正在編輯**的內容（`commit`）——即使雲端隨後才載入完成，這些都會擋下自動切換，避免靜默蓋掉使用者當下的工作。
  - **註**：離線提醒與回線自動補同步屬**後續階段（階段 B）**，本次未做；本階段僅處理「進場選版預設」與「不覆蓋使用者意圖」。契約見 [契約-預設最新雲端版](契約-預設最新雲端版.md)。

### `BpmnProvider`（`src/context/BpmnProvider.tsx`）
- 管理流程、模擬會話、模擬歷程、影響分析基準
- localStorage key：`bpmn-store`（穩定 key，與版本脫鉤），目前資料 `schemaVersion: 3`
- 載入時讀舊 key（`bpmn-store-v2`、`bpmn-store-v1`）作為 fallback，並透過共用 migration 框架升級
- 主要操作：`upsertProcess`、`deleteProcess`、`setSession`、`updateSession`、`addToHistory`、`captureBaseline`、`clearBaseline`

### Schema 版本管理（`src/services/migrations/`）
- **概念分離**：`schemaVersion`＝資料結構版本（migration 用）；`version`＝使用者面內容版本（發布遞增），兩者不混用。
- **通用框架** `runMigrations.ts`：線性遞增、缺欄位視為第 0 版、資料版本高於程式時拋錯。
- `orgMigrations.ts`（`ORG_SCHEMA_VERSION`，目前 **4**）與 `bpmnMigrations.ts`（`BPMN_SCHEMA_VERSION`）分別登記各自的升級步驟。
  - **v2→v3（`toV3`，2026-06-07）**：把舊資料殘留的 `assignment.level` 一律清空（設為 `undefined`），改用 `reportingDepth` 的主匯報深度自動計算。理由：既存 `level` 多為佈局產物／職等殘值，**非使用者刻意覆寫**；清空後一律走計算深度＝乾淨層級，之後才由使用者垂直拖曳產生真正的稀疏覆寫。歷史 `toV1` 的 `backfillAssignmentLevels` 不動，其回填值會被 `toV3` 清除（淨結果 `level = undefined`）。
  - **v3→v4（`toV4`，2026-06-08，「組別為主工作台」升級地基）**：為每個 `Group` 回填 `leaderId`（組長）。透過 helper `backfillGroupLeaders(data)`——`leaderId` 已有值的組**不覆蓋**；缺漏者以「組內匯報根」推回（`groupLeadership.deriveInGroupRoot`，與 `deriveGroupLeadership` 的回退組長共用同一演算法：組內「主管為 null 或主管在組外」的成員為候選，deterministic tiebreak 組內層級最高→組內部屬最多→employeeId 升冪）；**空組為 null**。**co-leader（平行共管）不進 schema**＝採推導不落地（`deriveGroupLeadership` 即時算）。
- 所有載入邊界（草稿、發布版本、seed/mock、匯入檔）都會跑 migration，匯出檔內含 `schemaVersion`。

## 9. 設計原則與慣例

- **services 為純函式**：商業邏輯與 React 解耦，利於測試與重用。
- **型別優先**：以 `src/types/` 的型別為單一事實來源；新欄位先補型別。
- **變更皆留痕**：所有 CRUD 透過 `orgOperations` 並寫入 `changeLog`。
- **草稿即時保存**：編輯自動寫 localStorage，避免遺失；正式保存則「發布版本」。
- **模擬可重現**：流程模擬擷取送出當下的 `orgContext` 快照，確保結果不受後續組織變動影響。
- **路徑別名**：`@` → `src/`。

## 11. 風險與未決事項

- **資料一致性（雲端寫穿）**：已有 opt-in 後端，寫穿為 **best-effort**（失敗僅 warn）。**離線偵測 + 未同步提醒（階段 B1）已落地**：後端啟用時，離線或寫穿失敗會以 `CloudSyncBanner` 提醒「離線中／有本機變更尚未同步」（`pendingCloudSync` 旗標、持久化）；但**仍無離線發布佇列／回線自動補推／衝突解決**（屬後續階段 B2），且後端尚無多人併發的版本合併策略，多裝置協作仍可能分歧。未啟用後端時則完全靠手動匯出入。
- **後端持久化粒度**：目前以 **JSONB 文件**保存整包 `OrgData` 快照（P4 才正規化為實體表），無法做實體級查詢與跨版本 diff（僅前端比對）。
- **無認證**：P1–P3 後端開放存取（CORS 限定來源），正式認證待 P6 / #2。對外部署前不可裸跑。
- **localStorage 容量**：大型組織 + 多版本 + 模擬歷程可能逼近瀏覽器配額，需評估清理或壓縮機制。
- **自動化測試**：已導入 Vitest，前端約 **523** 個測試（migration、核心 services、圖形建構、Provider、UI／互動／無障礙與 DOM 快照），後端含路由與 Prisma 整合測試；覆蓋率門檻 CI 強制。
- **lint**：既有 react-hooks/react-refresh 債已清零，CI lint 為硬性把關。
- **多分支部署複雜度**：CI 建置所有分支，分支數成長會拉長部署時間（型別檢查已由 `test.yml` 補回）。
