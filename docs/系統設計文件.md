# HR 組織架構調整工具 — 系統設計文件

> 本文件描述系統的整體需求、架構、資料模型與後續開發方向，作為團隊持續開發的依據。
> 內容以**現況程式碼**為準；標示〔現有〕為已實作、〔規劃中〕為尚未實作。
> 最後更新：2026-06-06。

---

## 1. 專案概述

**定位**：一個**純前端**的 HR 組織架構調整工具，協助人事維護公司人員的**組別歸屬**、**直屬／虛線主管**與**職級**，並以 [React Flow](https://reactflow.dev/) 視覺化組織匯報關係。在此基礎上，再延伸出 **BPMN 簽核流程設計、模擬與組織變更影響分析**。

**目標使用者**：HR / 組織治理人員、流程設計者。

**核心價值**：
- **矩陣組織視覺化**：支援「一人多組、每組可有不同主管」的矩陣組織，並以雙視角呈現。
- **安全試算**：所有變更先在草稿與快照中進行，可比對 diff、可發布版本，降低調整風險。
- **流程連動組織**：簽核流程的關卡可依組織關係（直屬主管、職級、組內職級、往上層級）動態解析簽核人，並能在組織變動時即時健檢出**斷鏈**或**單點風險（SPOF）**。

**關鍵特性**：無後端，資料自動存於瀏覽器 `localStorage`，並可匯出／匯入 JSON 做版本保存與共享。

## 2. 系統範圍

### 〔現有〕涵蓋功能
- 員工 / 組別 / 職級 / 組別歸屬（assignment）的維護
- 組織圖雙視角（匯報組織圖、組別歸屬圖）與圖上直接編輯
- 編輯模式快照（snapshot）與差異著色（diff）
- 變更歷程（changelog）與前後狀態 diff 檢視
- CSV 匯入（員工 × 組別）→ 產生組織 JSON
- 資料版本管理：草稿、內建種子／mock、發布版本、匯出入
- BPMN 流程清單／設計／模擬／影響分析
- GitHub Pages 多分支自動部署

### 〔規劃中〕非範圍（目前未實作，列為未來方向）
- 後端 API 與資料庫持久層（目前僅 localStorage + 檔案）
- 簽核流程的「生效日／排程生效」與正式送簽流程
- Azure AD / SSO 登入與權限控管
- Excel 大量匯入
- 多租戶 / 稽核合規

## 3. 整體架構

純前端 SPA，分為四層：

```
┌─────────────────────────────────────────────────────────┐
│  視覺化 / UI 層                                            │
│  React Flow 畫布、shadcn/ui 元件、頁面與表單              │
├─────────────────────────────────────────────────────────┤
│  狀態管理層（React Context）                               │
│  OrgProvider（組織資料）  /  BpmnProvider（流程與模擬）   │
├─────────────────────────────────────────────────────────┤
│  服務層（services/，純函式商業邏輯）                       │
│  圖形建構、diff、模擬器、影響分析、版本、CSV、匯出入       │
├─────────────────────────────────────────────────────────┤
│  資料層                                                    │
│  localStorage（草稿/版本/流程） + 檔案 I/O（JSON/CSV）    │
│  內建種子 src/data/org-data.json、mock、bpmn-defaults     │
└─────────────────────────────────────────────────────────┘
```

**資料流向**：
1. 使用者編輯 → React state 更新 → 自動寫入 localStorage 草稿
2. 重新整理 → 優先載入 localStorage 草稿；無草稿則載入當前「已發布版本」
3. 匯出 → 下載帶時間戳的 JSON；匯入 → 取代當前資料，可選擇發布為新版本
4. 流程模擬時，於送出當下擷取請款人的組織快照（orgContext），確保模擬結果可重現

## 4. 功能模組（依頁面）

入口 `src/App.tsx`，外層由 `OrgProvider` → `BpmnProvider` → `BrowserRouter` 包裹，所有頁面共用 `Layout`（頂部導覽 + `Outlet`）。

| 頁面元件 | 路由 | 說明 |
|----------|------|------|
| `PeoplePage` | `/`（index） | 人員與歸屬維護：新增／編輯員工、指派至組別並設定職級與主管 |
| `GroupsPage` | `/groups` | 組別階層維護：建立／編輯／停用組別、設定父子關係 |
| `OrgChartPage` | `/org-chart` | 組織圖雙視角 + 編輯模式（快照、diff 著色、節點拖曳排版） |
| `ChangeLogPage` | `/changelog` | 變更歷程稽核：時間軸列出所有操作，並可看前後 JSON diff |
| `CsvImportPage` | `/csv-import` | CSV 匯入：上傳「員工 × 組別」表 → 預覽 → 產生／下載 JSON |
| `BpmnListPage` | `/bpmn` | 流程清單與即時健檢（斷鏈 / SPOF 標示），建立／編輯／模擬／刪除 |
| `BpmnImpactPage` | `/bpmn/impact` | 影響分析：以基準快照比對組織變更對各流程簽核路徑的影響 |
| `BpmnDesignerPage` | `/bpmn/:processId` | 流程設計畫布：節點調色盤 + 畫布 + 屬性面板（關卡、條件、簽核門檻） |
| `BpmnSimulatePage` | `/bpmn/:processId/simulate` | 流程模擬：填請款表單、逐關卡解析簽核人、核准／駁回、模擬歷程 |

> 路由順序注意：`bpmn/impact` 必須宣告在 `bpmn/:processId` 之前，否則 `impact` 會被當成 processId。

**組織圖雙視角**：
- **匯報組織圖**：節點＝人員，連線＝匯報關係（實線＝主匯報、虛線＝其他主管）。
- **組別歸屬圖**：節點＝每筆組別歸屬，同一人跨組會出現多個節點；含組別標籤節點與外部主管節點。

## 5. 資料模型

型別定義位於 `src/types/`。

### 組織核心（`src/types/org.ts`）
- **`Employee`** — 員工：`id`、`employeeNo`（工號）、`name`、`status`（active/inactive）
- **`Group`** — 組別：`id`、`code`、`name`、`parentId`（階層父節點）、`status`
- **`JobLevel`** — 職級：`id`、`code`、`name`、`rank`（數字大小代表高低，供條件判斷）
- **`Assignment`** — 組別歸屬（核心關聯）：`employeeId`、`groupId`、`jobLevelId`、`supervisorIds[]`、`primarySupervisorId`、`isPrimaryGroup`、`level?`（組織深度，供 gateway 條件）
- **`ChangeEntry`** — 變更紀錄：`timestamp`、`operator`、`changeType`、`summary`、`before?`/`after?`（JSON 字串）
- **`OrgData`** — 整包資料：`schemaVersion`（結構版本，migration 用）、`version`（內容版本，發布遞增）、`exportedAt`、`employees[]`、`groups[]`、`jobLevels[]`、`assignments[]`、`changeLog[]`

> **設計重點**：`Assignment` 是矩陣組織的關鍵——主管與職級掛在「歸屬」上而非「員工」上，因此一人可在不同組有不同主管／職級。

### BPMN 流程（`src/types/bpmn.ts`）
- **`BpmnProcess`** — 流程：`nodes[]`、`edges[]`、`approvalThresholds[]`（職級→可簽核上限金額）、`status`、`version`
- **簽核人解析模式 `ApproverResolutionMode`**：`byJobLevel`（依職級）、`directSupervisor`（直屬主管）、`groupJobLevel`（組內指定職級）、`orgHierarchy`（沿匯報鏈往上至 rank 達標）
- **`SimulationSession`** — 模擬會話：`formData`（請款表單）、`resolvedPath[]`、`resolvedApprovers`、`orgContext`（送出時的組織快照）、`logs[]`、`status`
- **`ImpactBaseline`** — 影響分析基準：`capturedAt`、`label`、`data`（組織快照）

### 編輯工作階段（`src/types/editSession.ts`）
- **`OrgDiffResult`** — 各種變更集合（新增／移除／修改的員工、歸屬、邊）
- **`EditSnapshot`** — 編輯快照：`orgData` + `nodePositions`（組織圖節點座標）

## 6. 核心服務（`src/services/`）

皆為**純函式**，便於測試與重用：

| 服務 | 職責 |
|------|------|
| `buildOrgFlowGraph.ts` | 建構匯報組織圖的 React Flow 節點／邊，Dagre 自動排版（TB），回傳含層級線與邊界 |
| `buildGroupMembershipGraph.ts` | 建構組別歸屬圖（歸屬節點、組別標籤、外部主管），Dagre 分群排版 |
| `computeOrgDiff.ts` | 比對兩份 `OrgData` 的差異，供編輯模式 diff 著色 |
| `orgOperations.ts` | CRUD（upsert/delete 員工、組別、歸屬、import），並寫入 changelog |
| `exportImport.ts` | 檔案 I/O：clone、下載 JSON/CSV、解析；處理 UTF-8 BOM（Excel 相容） |
| `dataVersions.ts` | 掃描內建種子 + mock + 發布版本，回傳版本清單與驗證狀態 |
| `publishedVersions.ts` | 發布版本的儲存／還原與多版本打包（bundle）匯出入 |
| `csvParse.ts` / `csvToOrgData.ts` | 解析「員工 × 組別」CSV、驗證並產生 `OrgData` |
| `bpmnSimulator.ts` | 模擬器：建立會話、解析組織變數與關卡簽核人、評估 gateway 條件 |
| `processImpact.ts` | 影響分析：產生探測情境、健檢（斷鏈／SPOF）、比對基準與現況的路徑差異 |
| `assignmentLevels.ts` | 回填 assignment 缺失的 `level`（組織深度） |
| `validators.ts` | 驗證 `OrgData`、偵測匯報循環 |

## 7. 狀態管理

### `OrgProvider`（`src/context/OrgProvider.tsx`、`orgContextState.ts`）
- 管理組織資料、版本清單、當前版本、操作者
- localStorage keys：
  - `hr-org-draft` — 草稿（自動儲存）
  - `hr-org-active-version` — 當前選定版本
  - `hr-org-published-versions` — 本機發布版本清單（於 `publishedVersions.ts`）
- 主要操作：`selectDataVersion`、`publishVersion`、`saveEmployee`、`saveGroup`、`saveAssignment`、`removeEmployee`、`removeAssignment`、`loadFromFile`、`exportData`、`applyChange`

### `BpmnProvider`（`src/context/BpmnProvider.tsx`）
- 管理流程、模擬會話、模擬歷程、影響分析基準
- localStorage key：`bpmn-store`（穩定 key，與版本脫鉤），目前資料 `schemaVersion: 3`
- 載入時讀舊 key（`bpmn-store-v2`、`bpmn-store-v1`）作為 fallback，並透過共用 migration 框架升級
- 主要操作：`upsertProcess`、`deleteProcess`、`setSession`、`updateSession`、`addToHistory`、`captureBaseline`、`clearBaseline`

### Schema 版本管理（`src/services/migrations/`）
- **概念分離**：`schemaVersion`＝資料結構版本（migration 用）；`version`＝使用者面內容版本（發布遞增），兩者不混用。
- **通用框架** `runMigrations.ts`：線性遞增、缺欄位視為第 0 版、資料版本高於程式時拋錯。
- `orgMigrations.ts`（`ORG_SCHEMA_VERSION`）與 `bpmnMigrations.ts`（`BPMN_SCHEMA_VERSION`）分別登記各自的升級步驟。
- 所有載入邊界（草稿、發布版本、seed/mock、匯入檔）都會跑 migration，匯出檔內含 `schemaVersion`。

## 8. 技術棧與建置／部署

| 範疇 | 採用 |
|------|------|
| 框架 / 建置 | React 19、Vite 8、TypeScript（strict） |
| UI 元件 | shadcn/ui（base-nova 風格，底層 Base UI + Radix Slot） |
| 樣式 | Tailwind CSS v4、`tw-animate-css`、`class-variance-authority`、`clsx` + `tailwind-merge` |
| 圖示 / 字型 | `lucide-react`、Geist |
| 組織圖 | `@xyflow/react`（React Flow v12）+ `@dagrejs/dagre` |
| 動畫 | `@react-spring/web` |
| 路由 | `react-router-dom` v7 |

**環境需求**：Node 20.19+ 或 22.12+（Vite 8 要求）。

**常用指令**：
```bash
npm run dev               # 開發伺服器
npm run build             # tsc -b && vite build（型別檢查 + 打包）
npm run lint              # ESLint
npm run test              # Vitest 單次執行
npm run test:watch        # Vitest 監看模式
npm run test:cov          # 測試覆蓋率報告
npm run import:csv        # CSV → JSON CLI
npm run generate:csv-sample
```

**測試**：使用 **Vitest**（jsdom 環境），測試檔與來源並列（`*.test.ts`）。CI（`.github/workflows/test.yml`）於 push / PR 跑 lint、`tsc -b` 與測試。

**部署**（`.github/workflows/deploy-pages.yml`）：GitHub Pages 多分支策略——`git fetch --all` 建置所有活躍分支，各分支輸出至 `/hr-organization/{分支名}/` 子目錄，根目錄產生分支選單。base path 由 `VITE_BASE_PATH` 控制。CI 為求速度跳過型別檢查（僅 `vite build`）。

## 9. 設計原則與慣例

- **services 為純函式**：商業邏輯與 React 解耦，利於測試與重用。
- **型別優先**：以 `src/types/` 的型別為單一事實來源；新欄位先補型別。
- **變更皆留痕**：所有 CRUD 透過 `orgOperations` 並寫入 `changeLog`。
- **草稿即時保存**：編輯自動寫 localStorage，避免遺失；正式保存則「發布版本」。
- **模擬可重現**：流程模擬擷取送出當下的 `orgContext` 快照，確保結果不受後續組織變動影響。
- **路徑別名**：`@` → `src/`。

## 11. 風險與未決事項

- **無後端的資料一致性**：多裝置 / 多人協作需靠手動匯出入，易產生分歧；後端化前須有明確的版本合併策略。
- **localStorage 容量**：大型組織 + 多版本 + 模擬歷程可能逼近瀏覽器配額，需評估清理或壓縮機制。
- **自動化測試**：已導入 Vitest 並覆蓋 migration 與核心 services 純函式；元件/Provider 層測試與覆蓋率門檻仍待補強。
- **既有 lint 債**：components 有數個 react-hooks/react-refresh 告警待清理，CI 暫以 `continue-on-error` 不阻擋，需逐步修復。
- **多分支部署複雜度**：CI 建置所有分支，分支數成長會拉長部署時間（型別檢查已由 `test.yml` 補回）。
- **schema 版本管理**：已統一 migration 框架並修正 BPMN key/版本不一致；`OrgData.version` 與 `schemaVersion` 概念已分離（內容版本欄位 `version` 沿用，未更名為 `contentVersion`，列為可選後續）。
