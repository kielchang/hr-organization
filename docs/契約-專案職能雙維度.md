# 介面契約 — 專案職能雙維度（reporting line × function）

> 協調者（Software Architect）產出的**開發契約**。各角色照本契約各自開發，**不得自改契約**（要改回報協調者）。
> 對應方向：以 HR 規劃為定位，讓「專案職能」成為一等公民（見產品定位）。
> 狀態：草案 → 開工。最後更新：2026-06-06。

## 0. 目標與非目標

**目標**：HR 能沿兩個維度規劃組織——**reporting line（階層部門／匯報線）** 與 **專案職能（跨部門）**，並能以「職能視角」看誰服務哪些職能、跨職能負載、職能覆蓋缺口。

**v1 非目標（明確排除）**：職能階層／巢狀；匯入模板的職能標記欄；職能容量（headcount cap）與規劃指標（留給「規劃指標」方向）；正式送簽／SSO／多租戶（已降級，非本定位）。

## 1. 架構決策（ADR 摘要）

**採 Option A：在 `Group` 加 `kind` 判別子**。理由：重用既有矩陣模型（一人多歸屬、每組可有不同主管）；職能 lead 自然落在該職能 assignment 的 `primarySupervisorId`；後端 JSONB 文件**不需改 Prisma schema**；migration 只是回填。**不採** Option B（另立 `ProjectFunction` 實體）：動到每個 service／圖形／表單／匯入匯出，風險與 diff 過大。日後職能若需分歧屬性再演進。

## 2. 型別契約（`src/types/org.ts`）— 單一事實來源

```ts
/** 組別種類：department=階層部門（匯報線，走 parentId）；function=跨部門專案職能 */
export type GroupKind = 'department' | 'function';

export interface Group {
  id: string;
  code: string;
  name: string;
  parentId: string | null;
  status: EntityStatus;
  kind: GroupKind; // NEW，required（migration 回填，新表單必填）
}
```

## 3. Migration（`src/services/migrations/orgMigrations.ts`）

- `ORG_SCHEMA_VERSION` +1。
- 新步驟：每個缺 `kind` 的 group 補 `kind: 'department'`（舊資料＝全部視為部門）。
- 所有載入邊界（草稿／發布版本／seed／mock／匯入檔）皆已跑 migration，沿用即可；匯出檔含 `schemaVersion`。

## 4. 語意與驗證（`src/services/validators.ts`）

以**現有 `ValidationResult.errors` 機制**回報，**不擴張介面**：
- `department` 的 `parentId` 若非 null，必須指向另一個 `department`（function 不可當階層父節點）。
- `function` 的 `parentId` 在 v1 應為 `null`（職能扁平）。
- `Assignment.isPrimaryGroup === true` 的 group 應為 `department`（主歸屬＝home line）；指向 `function` 時回報明確訊息。

## 5. 服務（純函式）

- **`buildGroupMembershipGraph.ts`**：新增**可選** `kindFilter?: GroupKind` 參數；不傳＝不過濾（**向後相容**，既有呼叫與測試不受影響）。
- **新增 `src/services/functionCoverage.ts`（純函式）**，回傳職能視角資料：
  - 每個 `function` group 的成員清單（依 assignment）。
  - 每人所屬 function 數（跨職能負載）。
  - 無成員的 function（覆蓋缺口）。
  - 無 lead 的 function（該職能無任一 assignment 帶 `primarySupervisorId`）。
  - 型別放 `functionCoverage.ts` 內 export，供 UI 取用。

## 6. 表單／頁面（`src/components`、`src/pages`）

- **`GroupForm.tsx`**：新增 kind 選擇（部門／職能），預設「部門」。選「職能」時隱藏或停用 parent 選擇（v1 職能無階層）。
- **`GroupsPage.tsx`**：以 kind 分區或加徽章標示；建立／編輯可選種類。
- **`OrgChartPage.tsx`（組別歸屬視角）**：加「全部／部門／職能」過濾切換，接 `buildGroupMembershipGraph` 的 `kindFilter`。
- **職能視角呈現**：v1 先以上述過濾切換 + 一個輕量區塊呈現 `functionCoverage` 的關鍵訊號（無成員／無 lead 的職能、跨職能負載前幾名）。**不另開整頁**（最小可用）。

## 7. 匯入（v1 最小）

- `csvToOrgData.ts`（及 `xlsxToOrgData.ts` 若產生 group）產生的 Group 一律補 `kind: 'department'`。
- **不改** CSV/xlsx 解析管線；職能標記在 App 內後設。

## 8. 內建種子（`src/data/org-data.json`、mock）

- 既有 groups 補 `kind`；**手動把 2–3 個跨部門組別標為 `function`**，讓職能視角有示範資料（否則畫面空白）。

## 9. 後端（opt-in）— 確認即可

- 後端以 JSONB 文件保存整包 `OrgData`，`kind` 在文件內，**無 Prisma schema 變更**。
- 若 server 對 OrgData 做 zod 深度驗證 → 補 `kind`；否則確認 round-trip 即可。（Backend Architect 確認。）

## 10. 角色分派與邊界

| 角色 | 範圍 | 邊界 |
|---|---|---|
| 協調者（主執行緒） | 本契約、整合驗收 | 僅契約／文件 |
| 前端（Frontend Developer） | §2–§8 全部（`src/`），**不寫測試** | 不碰 `server/`、不改契約 |
| 後端（Backend Architect） | §9 確認 round-trip／zod | 僅 `server/` |
| 測試/QA（Test Results Analyzer） | migration／validators／functionCoverage／圖形過濾的測試；跑完整 `verify` | 僅測試碼，不改實作 |
| 程式碼審查（Code Reviewer） | 唯讀審查 §2–§8 | 只回報不改 |
| 文件（Technical Writer） | 系統設計文件第 1/2/5/6 節、待辦清單 | 僅文件 |

**驗收門檻**：`npm run verify`（前端）綠 + `npm run verify:server`（後端）綠 + 各角色把關通過 → 協調者在 `integration` 提交。
